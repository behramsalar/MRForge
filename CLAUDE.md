## 1. What this project is

A web-based application that lets researchers run MRI/fMRI analysis using tools already installed on the machine (mainly **FSL**, plus dcm2niix, the BIDS validator, ICA-AROMA later). It wraps these tools in a guided, reliable, good-looking workflow.

**The end goal is a polished, easy-to-use, pretty tool for lab members who are less experienced than the project owner.** The UI is the product, but the engine under it must be reliable, because novices cannot debug a failed FSL run themselves.

The central idea: a **Workspace** is a container for data and processing state. The app works the same for one scan, one subject, or a 100-subject dataset. There is no separate "group mode". Dataset-level controls appear automatically when relevant.

The UI looks linear (Import → Anatomical → Functional → Denoising → QC → Connectivity). Internally everything is modular steps with explicit dependencies.

## 2. Non-negotiable principles

1. **The UI never builds shell commands.** The path is UI → API → Step objects → job runner. Only Step classes know FSL command lines.
2. **No monolithic `preprocess_subject()`.** Every operation is a separate `Step` with declared inputs, parameters, outputs, dependencies, validation, logs and QC.
3. **Raw data is immutable.** `sourcedata/` and `rawbids/` are never modified after creation. All results go to `derivatives/`.
4. **Provenance for every run.** Record command, parameters, input files (with hashes), output files, tool versions, return code, stdout, stderr, start and finish times.
5. **Resume, don't redo.** A completed and valid step is never rerun. A failed pipeline resumes at the failed step.
6. **Flag, don't decide.** QC can warn, but only the researcher accepts or excludes a subject, with a recorded reason.
7. **Facts come from metadata.** Reports and the methods text are generated deterministically from recorded provenance, never written by an LLM from memory.
8. **Plain-language errors.** Every failure shows: what happened, why it probably happened, and what to do next. The raw log stays one click away.
9. **Safe defaults, advanced options hidden.** Only offer actions whose inputs exist. Guardrails over warnings.
10. **Never invent FSL flags or behavior.** Verify against `--help`, the FSL documentation, or by running on test data. If a scientific choice is uncertain, mark it `# REVIEW(domain)` and list it for the user at the end of the stage.
11. **Honest status.** Say exactly what was run, what passed, and what was not tested. Never claim tests pass without running them.

| Component | Choice |

## 4. Environment rules

- FSL, dcm2niix and the BIDS validator must be callable from the same shell Claude Code runs in. `scripts/check_env.py` verifies this.
- Never modify the FSL installation or anything outside the project folder and the workspace data folders.
- Test data lives outside the repo (path in section 0). Never commit imaging data. Keep test subjects tiny (few volumes, small matrix) so tests run fast.
- Integration tests that need FSL are marked `@pytest.mark.fsl` so unit tests can run without FSL.

## 5. Workspace layout on disk

```text
<workspace>/
    workspace.json           # name, created, schema version
    db.sqlite                # state index (rebuildable from provenance where possible)
    sourcedata/dicom/        # original DICOMs, never modified
    rawbids/                 # BIDS dataset: dataset_description.json, participants.tsv, sub-*/{anat,func,fmap,dwi}
    derivatives/<appname>/
        sub-XXX/ses-YY/<step-name>/
            outputs...
            provenance.json  # written next to the outputs, travels with them
            logs/            # stdout.log, stderr.log
    reports/
```

Internal entities (define early, even if some stay thin): `Workspace, Subject, Session, Acquisition, File, Pipeline, PipelineRun, ProcessingStep, Job, QCResult, UserDecision, Report, Atlas, ROI`.

The researcher is never forced to think about these layers. One imported scan simply becomes a workspace with `sub-001`.

## 6. Core engine design

### Step contract

```python
class Step:
    name: str
    version: str                 # bump when behavior changes; part of the resume hash
    InputSpec / ParamSpec / OutputSpec   # pydantic models

    def validate_inputs(self, ctx) -> list[Problem]
    def prepare(self, ctx) -> None
    def run(self, ctx) -> StepResult       # builds and executes commands
    def validate_outputs(self, ctx) -> list[Problem]
    def generate_qc(self, ctx) -> list[QCItem]
    def register_outputs(self, ctx) -> None
```

### Job states
`Queued, Running, Completed, Failed, Cancelled, Interrupted`

On startup the runner marks any stale `Running` job as `Interrupted` (process was killed or machine rebooted).

### Resume rule
A step run is reusable only if all hold: status `Completed`, same step version, same parameter hash, same input file hashes, all registered outputs exist and pass `validate_outputs`. If an upstream step changes, downstream steps are invalidated. Resume starts at the first step that is not reusable.

### Errors
Steps raise structured errors with a `code`, a plain-language `message`, a `suggested_action`, and a link to the raw log. Maintain an error catalog in `docs/errors.md`. Raw FSL output is never the only thing shown.

## 7. How we work

### 7.1 Session start
1. Read `CLAUDE.md`, `PROGRESS.md`, `docs/architecture.md`, `docs/DECISIONS.md`.
2. State in two or three lines where we are and what the next sub-step is.
3. Do not start work from a later stage than the current one.

### 7.2 Planning
- At the start of each **stage**, use plan mode: propose the plan and the file layout, then wait for the user's approval.
- Work in **small sub-steps** (the lettered items in section 8). One sub-step = one focused task, one commit.

### 7.3 Testing as we build
- Every sub-step ships with automated tests (unit tests, plus `@pytest.mark.fsl` integration tests where real FSL is involved).
- Test resume logic by actually killing processes, not by mocking.
- For scientific steps, compare against a manual FSL run on the same data (see Stage 5).

### 7.4 Sub-step checkpoint ("quick check")
After each lettered sub-step, before moving on:
1. Run the automated tests and report the real results.
2. Give the user a **Quick check**: one to three exact commands to run and what the expected output looks like.
3. Wait for the user to say it looks right, or continue only if the user told you to batch sub-steps.

### 7.5 Stage-end protocol
When a stage's last sub-step is done:
1. Run the full automated test suite and report results (including failures and skipped tests).
2. Update `PROGRESS.md`.
3. Print the stage's **Manual test checklist** with exact commands, what to look at, and expected outcomes.
4. List every `REVIEW(domain)` item and every assumption made.
5. **STOP.** Wait for the user to confirm "stage accepted" before touching the next stage.

### 7.6 Git
- Branch per stage: `stage-N-short-name`. Commit per sub-step with a clear message.
- After the user accepts a stage: merge to `main` and tag `stageN-accepted`.
- Never commit data, secrets, or large generated files.

### 7.7 Domain review
Claude Code writes the code; the user reviews neuroimaging choices. Anything involving FSL parameters, QC thresholds, registration choices, or defaults is flagged `# REVIEW(domain)` in code and listed in the stage-end summary. Defaults in this file that come from the roadmap (for example 5 discarded volumes, 5 mm smoothing, 150 s high-pass) are **proposals the user must confirm**.

### 7.8 Asking vs. deciding
Ask the user when a choice affects architecture, data layout, scientific defaults, or visible design. Decide yourself for local implementation details. Record every non-trivial decision in `docs/DECISIONS.md` (date, decision, reason).

### 7.9 Progress tracking
Keep `PROGRESS.md` current: stage, sub-steps (done / in progress / not started), known issues, open questions, next action.

### 7.10 When something I told you here is wrong
If you discover that an instruction in this file doesn't match reality (an FSL command behaves differently, a library lacks a feature), say so, propose a fix to this file, and wait for the user's approval.

- 0c. `docs/architecture.md`: Step contract, workspace layout, job and provenance schema, resume rule, error model, glossary. End it with an **Open questions** section for the user.
- 0d. `docs/DECISIONS.md`, `docs/TEST_DATA.md` (what test data is needed, where it lives, how it is described), `PROGRESS.md`.

**User tasks (not Claude Code)**
- Install and verify FSL, dcm2niix, BIDS validator.
- Pick one small public fMRI dataset (for example from OpenNeuro) with a T1 and a resting BOLD, plus one DICOM sample set. Record them in `docs/TEST_DATA.md`.
- **Review `docs/architecture.md` carefully.** This is the most important review of the project.
- In parallel with Stage 1: talk to 2–3 lab members, write down where they get stuck with FSL today, and sketch the key screens (import and confirm series, run a step, QC review, error screens). Save notes in `docs/ux-notes.md`.

**Manual test checklist**
- `python scripts/check_env.py` shows correct versions for your machine.
- `pytest` runs and passes (smoke test only at this point).
- You have read `architecture.md` and answered its Open questions.

### Stage 1 — Headless engine (CLI only, no web)

**Build, in this order**
- 1a. Data models and SQLite persistence (Workspace, Subject, File, Job/StepRun), minimal.
- 1b. `Step` base class, step registry, pydantic parameter/input/output specs.
- 1c. Job runner: subprocess execution, log capture, command recording, return code, state machine, stale-job detection on startup, configurable max concurrency, `JobQueue` interface with a local implementation.
- 1d. Provenance writer and resume logic exactly as in section 6, including downstream invalidation.
- 1e. CLI: `mrforge workspace create`, `mrforge run <step> ...`, `mrforge status`, `mrforge resume`, `mrforge log <job>`.
- 1f. `FakeStep` for tests: configurable duration, can fail at a chosen point, writes dummy outputs.
- 1g. `BetStep` (FSL `bet`) as the first real step.
- 1h. `FslAnatStep`: wraps `fsl_anat`, handles its `.anat` output directory, registers the key outputs (bias-corrected, brain, segmentation, registration transforms), validates them.

**Quick checks along the way**
- After 1e/1f: run a pipeline of fake steps with a failure at step 3, then `mrforge resume` and confirm steps 1–2 are not rerun.
- After 1g: run `bet` through the app and manually with the same options, then compare outputs.

**Manual test checklist**
1. `mrforge workspace create demo` then run `bet` on a test T1. Open the result in FSLeyes and compare with your own manual `bet` run. They should be identical.
2. Start `fsl_anat` and `kill -9` the process while it runs. `mrforge status` must show `Interrupted`, not `Running`.
3. `mrforge resume` continues correctly and the final result matches a manual `fsl_anat` run.
4. Rerun the same step with unchanged inputs: it must report "already completed" and not run.
5. Change one parameter: that step reruns, and any downstream step is invalidated.
6. Delete one output file by hand: the step is detected as invalid and reruns.
7. Look at `provenance.json` and the logs: command, versions, parameters and return code are all present.
8. Force a failure (bad input file): the error shows a plain-language message and suggested action, with the raw log reachable.

### Stage 2 — Import and BIDS (still CLI)

**Build**
- 2a. DICOM folder/ZIP scan and series metadata reading (pydicom): SeriesDescription, ProtocolName, ImageType, Modality, volume count, dimensions, TR, TE, echo number, diffusion gradients, phase-encoding direction.
- 2b. Series classification from multiple signals with a confidence level (High / Medium / Low). Rules live in a plain config file (`classification_rules.yaml`), with unit tests built from real examples. Unknown or low-confidence series are never silently assigned.
- 2c. dcm2niix conversion with recorded command and version.
- 2d. BIDS organizer: `dataset_description.json`, `participants.tsv`, `sub-*/anat|func|fmap|dwi`, JSON sidecars, `IntendedFor` assignment for fieldmaps.
- 2e. BIDS validator integration, with a translation layer from validator messages to plain-language warnings plus a suggested fix.
- 2f. Import of existing NIfTI files and existing BIDS datasets (BIDS import should skip conversion and just register the data).

**Manual test checklist**
1. Run import on one of your real DICOM sets. Review the detection table: series, detected type, confidence. Every series should be correct or clearly flagged.
2. Correct a deliberately misclassified series through the CLI and confirm the correction is used.
3. Open the converted NIfTI files in FSLeyes and check that orientation and volume counts are right.
4. Check the BIDS folder structure by eye; the validator reports no errors, and warnings are shown in plain language.
5. Import an existing BIDS dataset (your test dataset) and confirm nothing is reconverted.
6. Run the import twice: the second run must not duplicate or corrupt anything.
7. Try a messy case (missing series, odd naming) and confirm the app flags it instead of guessing.

### Stage 3 — First vertical slice (backend API + minimal real UI)

**Goal:** prove the architecture end to end with the real component library. Layout stays simple, but nothing is throwaway.

**Build**
- 3a. FastAPI endpoints: workspaces, subjects, files, series classification, jobs, step runs, logs. Auto-generated OpenAPI schema; the frontend uses a generated typed client.
- 3b. Short comparison document: NiiVue vs VoxelLab for the embedded viewer (features, effort, licensing, overlay support). **Wait for the user's decision.**
- 3c. Propose 2–3 component library options with a quick visual sample each. **Wait for the user's decision**, then set up design tokens (colors, type scale, spacing, radii) in one file and document them in `docs/design-system.md` and a short section at the end of this file.
- 3d. Redis + RQ adapter behind `JobQueue` only if the API and worker need to run separately.
- 3e. Frontend screens: workspace list/create → import → confirm series (table with confidence, editable) → run anatomical preprocessing → job status with live updates → viewer with overlays.
- 3f. Failure UX: interrupted/failed job screen with plain-language error, **View log**, **Retry step**, **Resume pipeline**.

**Manual test checklist**
1. In the browser, go from DICOM folder to a viewed `fsl_anat` result without using the terminal.
2. Kill the backend while `fsl_anat` runs, restart it: the job shows as Interrupted and Resume works.
3. Feed a bad input: a readable error appears, with an obvious next action.
4. Refresh the page or open it from another device mid-job: status stays correct.
5. Open the viewer on the T1 with the brain-extraction or segmentation overlay, and check that overlays align.
6. Check that the UI only uses components and tokens from the design system (no one-off styles).

### Stage 4 — Lab user test and design pass (user-led)

**User tasks**
- Have a less experienced lab member run the Stage 3 flow with no help from you. Watch silently and write down every hesitation and confusion in `docs/ux-findings.md`.

**Claude Code tasks**
- 4a. Turn `docs/ux-findings.md` into a prioritized fix list and propose it to the user.
- 4b. Apply the approved fixes and refine the design system (tokens, components, copy, empty states, error wording).
- 4c. Finalize `docs/design-system.md` and add a "UI rules" section to this file.

**Manual test checklist**
- A second, different lab member completes the flow with fewer or no stumbles than the first.

### Stage 5 — Functional preprocessing (one step at a time)

Each sub-step is its own `Step` with its own QC output, tests, and a **comparison against a manual FSL run on the same data**. Verify every command against FSL documentation and `--help` before writing it.

**Build**
- 5a. Discard initial volumes (default proposal: 5; user confirms).
- 5b. Motion correction (MCFLIRT) with motion parameters, absolute/relative displacement and framewise displacement, plus a motion plot.
- 5c. Fieldmap preparation and distortion correction. Confirm with the user which fieldmap type(s) their scanner produces before implementing.
- 5d. Spatial smoothing (default proposal: 5 mm FWHM).
- 5e. Temporal filtering (default proposal: 150 s high-pass).
- 5f. Functional → T1 registration (BBR) with a registration QC mosaic (axial/coronal slices with outline overlay) and **Open interactively** button into the viewer.
- 5g. Apply the T1 → MNI nonlinear warp from `fsl_anat` to produce analysis-ready BOLD.
- 5h. Functional preprocessing screen: a clean parameter form with defaults, advanced options hidden, and only valid choices shown (for example, "Use fieldmap" disabled if no fieldmap exists).
- 5i. Optional slice-timing correction (off by default).

**Manual test checklist** (after each of 5a–5g, then once at the end)
1. Run the step in the app and the same operation manually with FSL on the same data. Outputs match (identical, or differences explained and documented).
2. Check the QC image or plot by eye. It should make an obvious failure obvious (try a deliberately bad input).
3. Run the whole functional pipeline from the UI on the test dataset and open the final result in the viewer.
4. Interrupt mid-pipeline and confirm resume starts at the right step.
5. Review the list of `REVIEW(domain)` items with Claude Code.

### Stage 6 — Batch, resources, QC decisions

**Build**
- 6a. Multi-subject selection and batch runs using the same pipeline (no special "group mode").
- 6b. Resource scheduler: max simultaneous subjects, CPU threads per subject, total CPU cap, memory reserve, and Balanced / Max performance / Low impact presets. Jobs wait instead of oversubscribing the machine.
- 6c. QC decision workflow: per-subject Accept / Review / Exclude with a required reason, stored as provenance. Motion summary (mean/median/max FD, number of volumes above threshold) with warnings that flag but never exclude.
- 6d. Dataset dashboard (counts of processed / failed / needs review / excluded, subject table).

**Manual test checklist**
1. Run the pipeline on 5–10 subjects. The machine stays responsive and the resource limits are respected (watch `htop`).
2. Deliberately break one subject. Only that subject fails; the others finish; the dashboard shows it clearly; resume works for that subject only.
3. Record QC decisions, restart the app, and confirm they persist with reasons.
4. A high-motion subject is flagged but not excluded automatically.

### Stage 7 — Reports and system page (completes MVP 1)

**Build**
- 7a. HTML preprocessing report per subject: acquisition, structural and functional processing, motion, registration, QC, warnings, user decisions, software versions, parameters, commands.
- 7b. Command history / provenance viewer (with **Copy command** and **Re-run**).
- 7c. System status page (the Stage 0 environment checks in the UI).

**Manual test checklist**
- Generate a report for a processed subject and verify every number against the logs and `provenance.json`.
- A colleague who didn't build the app can understand what was done to a subject from the report alone.
- Tag the release (`v0.1`) after the user accepts.

### Later (do not start without an explicit go-ahead)

Each follows the same pattern: backend step with tests and a comparison against manual FSL, quick check, then its screen in the agreed design, then a manual test checklist.

- **MVP 2:** MELODIC, manual ICA component classification screen (signal / noise / uncertain → `fsl_regfilt`), WM/CSF/motion nuisance regression with mask preview, ICA-AROMA, before/after denoising QC, deterministic methods-text generator, motion scrubbing.
