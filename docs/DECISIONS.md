## 2026-10-04: Stage 5 is built on FEAT (design.fsf), not on separate re-implemented steps
User decision (they asked why FEAT's own design file is not used, and described their previous workflow: FEAT, then cleanup, then `applywarp` to MNI). Spike results: `feat design.fsf` runs headless and without a queue; a 60-key pre-stats design gives bit-identical output to the full GUI-generated design; FEAT writes `<name>+.feat` if the folder exists, so the step clears its own leftover first; with a fieldmap FEAT's `mainfeatreg` runs `epi_reg --fmap` and unwarps the 4D data itself (after motion correction, before smoothing); FEAT finds the whole-head T1 and fieldmap magnitude by stripping `_brain` from the file name and the white-matter image as `<name>_wmseg`, so the step stages renamed hard links (white matter = label 3 of the `fsl_anat` segmentation). FEAT is deterministic here: a manual `feat` run on MRForge's saved design gives an identical `filtered_func_data`.
Smoothing (5 mm) and high-pass (150 s) are inside FEAT, before cleanup (user's choice); standard space reuses the `fsl_anat` warp in a later step (user's choice).

## 2026-10-04: QC results are stored in provenance.json
`StepResult.qc` and warnings were computed but never saved. The worker now writes them into `provenance.json` (`qc`, `warnings`), so reports and the UI can show them later. QC images live next to the results (`*_qc.png`, listed in `.bidsignore`).

## 2026-10-04: Framewise displacement is computed by MRForge
Power et al. 2012 formula (head radius 50 mm) from FEAT's six realignment parameters. `fsl_motion_outliers --fd` gives similar but not identical numbers on the same data (it runs its own `mcflirt`, so its parameters differ slightly: on the 20-volume test cut the values differed by up to about 10 percent), so it is not used as an exact reference. Only metrics are reported; thresholds and decisions belong to Stage 6c.

## 2026-10-04: Light researcher profiles (not a login); CLAUDE.md section 9 amended
The user wants researchers to follow and resume their own work and asked whether a real login would be hard later. Decision: build light profiles now, shaped so that accounts can be added without a rewrite. A profile is a name stored in an app-level store (`researchers.sqlite` next to the app settings, `accounts.py`), chosen in the browser and sent as the header `X-MRForge-User`. Operations record the name that started them (`operation.started_by`, workspace schema 4, older workspaces upgrade themselves). The API finds the current researcher in one function (`current_researcher`); a login would add a password hash to the table and replace that function with a session check, plus protecting every route (including the live-update stream and image URLs), HTTPS and workspace permissions. Profiles are NOT security: anyone can pick any name, so they must never be used to protect data. Names are unique ignoring case.

## 2026-10-04: Viewer is a global page; the image list is built from BIDS names
The Viewer page lists every raw image and result of a subject (grouped Raw data / Anatomical results / Functional results / Fieldmap results, with plain-language names built from the BIDS file names in `viewerimages.py`; transforms and the native `.anat`/`.feat` folders are not listed). Any image can be the shown image or an overlay (opacity and colour map per overlay, volume slider for time series); a link can name the image (`#/w/<ws>/viewer/<subject>/<relpath>`). A broken page now shows a plain message with a reload button instead of a blank screen (`ErrorBoundary`). Known limits left for later: no side-by-side comparison, no persistent viewer settings, large time series are read whole by the browser.

## 2026-10-05: Full processing is a registry of stages; Process is a tree in the sidebar
Full processing (the default way to start work) plans an ordered list of **stages** from `backend/mrforge/processing.py`: Anatomical, Functional, Standard space. A stage describes itself in plain language, plans its steps, and updates a shared context (`bold[run]` is the native-space time series the next stage should use). New stages the user named (artifact rejection, WM/CSF regression, ROI-to-ROI correlation) are added to `STAGES`; cleanup stages go between Functional and Standard space, so cleanup comes before MNI and Standard space automatically takes the cleaned data. The confirmation dialog is generic: it shows whatever stages the plan returns (checkbox, description, per-recording settings, reasons for what is left out). `PipelineStep.label` (separate from `id`) lets one pipeline hold the same step for several recordings with tidy result names. The sidebar shows Process as a tree: Full processing (default), Anatomical, Functional; later kinds of processing become more children.
Anatomical results that exist but were not made by a recorded MRForge run are made again unless the stage is unticked (the dialog says so): MRForge only skips work it has a record of.

## 2026-10-05: An import can be undone as a whole (exception to raw-data immutability)
The user could not change an import once written (skipping a series or renaming a task was refused; the only advice was "new workspace"). Decision, chosen by the user: a button/command **undoes a whole import** on purpose. It removes only the files that import wrote into `rawbids/` (images and sidecars, checked against the recorded hashes; images changed since are never removed and the undo is refused), removes empty folders, the subject's row in `participants.tsv` and in the database when nothing of it remains, and drops `IntendedFor` entries that point at removed runs. It keeps the converted copies and scanner files (rawbids files are hard links to the converted copies, so nothing is lost), keeps the user's decisions so they can be edited, writes `imports/<id>/undo-log.json` (who, when, what), and marks the manifest `undone`. Processing results are not deleted: steps whose inputs are gone are simply no longer up to date (the dialog lists them). Refused while a step is running. Single-series changes were not chosen (run numbering and fieldmap links would need rewriting).

## 2026-10-05 MELODIC is made reproducible; labels are tied to one decomposition
- MELODIC starts from random values: without a fixed seed, repeated runs on identical data gave different components in a different order (seen on real data: the same pattern was component 5, then 4). The step now passes `--seed` (default 1, a parameter, recorded; REVIEW(domain)). Verified: same seed gives byte-identical mixing matrices; another seed differs.
- Consequence for Stage 6b: the saved label file must record which decomposition it belongs to (hash of the mixing matrix) and the review screen must refuse or warn if MELODIC was re-run with a different seed or settings, since component numbers then mean something else.
- Slice summary: a slice every 5 mm through the whole brain in all three planes, cropped to the brain, so small areas are not missed (earlier: 7 slices per plane).

## 2026-10-07 ICA-AROMA (6f)
- Installed the reference implementation (https://github.com/maartenmennes/ICA-AROMA, Apache 2.0), pinned to commit 302f30d (2024-02-22, 21 commits after tag v0.4.4-beta; the tag lacks the `-noplots` option and has another `mask_edge.nii.gz`). It lives in `tools/ICA-AROMA` (git-ignored) via `scripts/install_aroma.sh`; the only package added to the Python environment is `future`. Its pinned requirements (numpy 1.14, matplotlib 2.2, ...) are not installable on current Python and are not needed: it runs with the current numpy, scipy, pandas, matplotlib and seaborn. The PyPI refactor `ica-aroma-py` was not used because its results were not checked against the reference.
- `aroma_classify` runs AROMA's classification only (`-den no`) on the existing MELODIC result (`-md`), with the FEAT motion parameters, the T1 affine and the fsl_anat T1->MNI warp; removal stays with our `regfilt` (partial regression, same as AROMA's non-aggressive option). Verified: same classification as ICA-AROMA run by hand (38 of 57 components on the demo run).
- Three ways to label (stage option): you; ICA-AROMA proposes and you confirm (pause); ICA-AROMA decides (no pause; the decision record says so). AROMA modes are offered only when AROMA is installed.
- Caveats for the researcher (REVIEW(domain)): AROMA's authors recommend running it on data WITHOUT temporal filtering (high-pass) and with about 6 mm smoothing; our FEAT result is high-pass filtered (150 s) and 5 mm smoothed, because filtering is done inside FEAT before cleanup as decided in Stage 5. On the demo run AROMA proposed 38 of 57 components as motion, with high edge fractions for most components; only about 59% of the component mass lies inside the MNI brain mask. Treat the automatic mode with care and compare with your own labelling on a few subjects before trusting it.
